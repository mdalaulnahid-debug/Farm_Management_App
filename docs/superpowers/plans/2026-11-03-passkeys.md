# Passkey Sign-In Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Staff sign in with one touch (fingerprint, face, Windows Hello or the device PIN) through a passkey. Password
plus the 2-step code stays as the backup way in.

**Architecture:**
- **`auth/passkeys.ts`** (new) holds the pure pieces:
  - which address the passkey belongs to (relying-party ID and origin);
  - one-use challenges kept in memory;
  - a device name guessed from the browser.
- **`routes/passkeys.ts`** (new) holds the routes. It uses `@simplewebauthn/server` and a new additive `Passkey`
  table.
- **The session start** (cookie, audit, reset of failed tries) moves out of `routes/auth.ts` into `auth/auth.ts`,
  so password sign-in and passkey sign-in share it.
- **The web app** uses `@simplewebauthn/browser` on the sign-in page and in My settings → Password & security.

**Tech Stack:**
- Fastify 5, Prisma 6 on SQLite, Zod, React 19, Vitest.
- `@simplewebauthn/server@14.0.3` and `@simplewebauthn/browser@14.0.0`, pinned exactly (both published in September
  2026; Node ≥ 20).

**Spec:** `docs/superpowers/specs/2026-11-03-app-backups-passkeys-design.md` (Part 3)

## Global Constraints

- **Schema: additive only.** One new `Passkey` table, plus the `passkeys` relation on `User`. `prisma db push` runs
  unattended, so there is no `--accept-data-loss` and no change to existing columns.
- **Every passkey check needs `userVerification: 'required'`:** when it is made, and at every sign-in. There is no
  path that skips the fingerprint, face or PIN.
- **A passkey exists only alongside 2-step sign-in:**
  - adding one needs 2-step already on, plus the password;
  - turning 2-step off yourself, the admin "Reset 2-step sign-in", and the console password reset all remove the
    person's passkeys.
- **Password plus 2-step code keeps working, unchanged.** The existing lockout, session, forced-password-change
  and permission rules are unchanged.
- **A passkey sign-in counts as a 2-step sign-in.** Its audit row reads `signed in (passkey)`.
- **A failed passkey check** is recorded as `login_failed`, but **does not** count toward the account lock.
- **Rate limit:** the same as password sign-in, 10 per minute, on both passkey sign-in routes.
- **Challenges** last 5 minutes, live in memory, and each can be used once.
- **No secret material in responses or logs.** The public key is never returned.
- **Passkeys need HTTPS.** Plain `http://` is allowed only for `localhost`, as browsers allow. An optional
  `PASSKEY_ORIGIN` setting pins the address.
- **Every user-facing string** in English and Bangla.
- **No farm-specific addresses** in committed files (the repository is public).
- **Each new route** gets a row in `test/permissions.test.ts`.
- **Testing:** browser checks only on port 4400 with a throwaway database. Never touch port 4000 or the live
  database.

## Settings (new, optional)

- `PASSKEY_ORIGIN`: for example `https://farm-name.tailnet.ts.net`. When set, it is the only accepted origin, and its
  host is the relying-party ID. When unset, both come from the request (protocol and `Host`).

## Review Focus

1. **Behind `tailscale serve` the server sees a different host or protocol than the browser.** Without the setting,
   every passkey fails. With `PASSKEY_ORIGIN` set, the request's own host is ignored. (Task 1 test.)
2. **Two sign-ins sent in parallel with the same signed answer.** Exactly one succeeds, because the challenge is
   taken before any `await`. (Task 2 test.)
3. **The passkey was deleted on the phone but is still listed on the server, or the reverse.** The phone offers a
   passkey the server doesn't know. The answer is 401 "This passkey is not set up here any more. Sign in with your
   password.", not a 500. (Task 2 test.)
4. **The same device is added twice.** The options list the person's existing passkeys in `excludeCredentials`, so
   the device refuses a second one. (Task 2 test.)
5. **A copied passkey (its counter goes backwards).** It is refused, and the try is recorded. (Task 2 test.)

**The model:**
```prisma
model Passkey {
  id           String    @id @default(cuid())
  userId       String
  user         User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  credentialId String    @unique // base64url, as the browser sends it
  publicKey    Bytes
  counter      Int       @default(0)
  transports   String?   // JSON array
  name         String
  createdAt    DateTime  @default(now())
  lastUsedAt   DateTime?
  @@index([userId])
}
```

**Interfaces:**
- Produces, in `auth/passkeys.ts`:
  - `relyingParty(req: { protocol: string; host: string; hostname: string }): { rpID: string; origin: string } | null`
    - With `PASSKEY_ORIGIN` set: that origin, and its hostname as the `rpID`.
    - Otherwise, from `req`: `https` with any host, or `http` only when the host is `localhost`.
    - `null` otherwise.
  - `issueChallenge(kind: 'register' | 'login', challenge: string, userId: string | null): string`: returns a
    challenge id. Each one lasts 5 minutes, and expired ones are swept on each issue.
  - `takeChallenge(id: string, kind: 'register' | 'login'): { challenge: string; userId: string | null } | null`:
    synchronous and one-use. It deletes the challenge before returning it. A wrong kind or an expired challenge
    gives null.
  - `deviceName(userAgent?: string): string`:
    - `"iPhone"`, `"iPad"`, `"Android phone"`, `"Windows PC"`, `"Mac"`, or `"This device"` otherwise;
    - followed by `" · Chrome"`, `" · Edge"`, `" · Safari"` or `" · Firefox"` when the browser is known;
    - at most 60 characters.
- Produces, in `test/helpers/soft-authenticator.ts` (built with `node:crypto` P-256 keys and `isoCBOR` from
  `@simplewebauthn/server/helpers`):
  - `class SoftAuthenticator`;
  - `register(options: PublicKeyCredentialCreationOptionsJSON, origin: string, opts?: { uv?: boolean }): RegistrationResponseJSON`.
    This uses the `none` attestation. The flags are UP (0x01), UV (0x04, unless `uv: false`) and AT (0x40).
  - `assert(options: PublicKeyCredentialRequestOptionsJSON, origin: string, opts?: { uv?: boolean; counter?: number; credentialIndex?: number }): AuthenticationResponseJSON`.
    It signs `authData ‖ sha256(clientDataJSON)` with ECDSA-SHA256 in DER form. The counter goes up by 1 per
    call unless `counter` is given. `userHandle` is the `user.id` from registration.

**Routes**, under `/api/v1`:

| Route | Guard | Body → result |
|---|---|---|
| `GET /auth/passkeys` | `can()` | → `{ available: boolean, twoStepOn: boolean, data: [{ id, name, createdAt, lastUsedAt }] }` |
| `POST /auth/passkeys/options` | `can()`, 10/min | `{ password }` → `{ challengeId, options }` |
| `POST /auth/passkeys` | `can()`, 10/min | `{ challengeId, response, name? }` → `{ id, name }` |
| `PATCH /auth/passkeys/:id` | `can()` | `{ name }` (1–60 characters) → `{ ok }` |
| `DELETE /auth/passkeys/:id` | `can()` | → `{ ok }` |
| `POST /auth/passkey/login/options` | public, 10/min | → `{ challengeId, options }` |
| `POST /auth/passkey/login` | public, 10/min | `{ challengeId, response }` → `{ ok }` plus the session cookie |

**Rules:**
- **Without a usable address** (`relyingParty(req)` is null), every route except `GET` returns 400: "Passkeys work only
  on the https address of FarmLedger."
- **Adding options:**
  - 409 "Turn on 2-step sign-in first." when `totpEnabledAt` is null;
  - 400 "Password is incorrect." for a wrong password;
  - `generateRegistrationOptions` with:
    - `rpName`: the organization name;
    - `userName`: the email;
    - `userDisplayName`: the name;
    - `userID`: the UTF-8 bytes of `user.id`;
    - `attestationType: 'none'`;
    - `excludeCredentials`: the person's passkeys;
    - `authenticatorSelection: { residentKey: 'required', userVerification: 'required' }`.
- **Adding:**
  - the challenge must be a `'register'` one for this same user;
  - `verifyRegistrationResponse(..., requireUserVerification: true)`;
  - the name defaults to `deviceName(user-agent)`;
  - audit `Added a passkey "<name>"`.
- **Sign-in options:** `generateAuthenticationOptions({ rpID, userVerification: 'required', allowCredentials: [] })`.
- **Sign-in:**
  1. `takeChallenge` comes first, synchronously. If it fails: 401 "The sign-in took too long. Try again."
  2. Find the passkey by `response.id`. If there is none: 401 "This passkey is not set up here any more. Sign in
     with your password."
  3. If the user is inactive, or has no `totpEnabledAt`: 401 "Sign in with your password."
  4. If the account is locked: 401 with the existing locked message.
  5. Run `verifyAuthenticationResponse` with `requireUserVerification: true`, and with `credential` built from the
     stored row.
     - If it throws or is not verified: audit `login_failed` with
       `Failed sign-in for <email> (passkey check failed)`. **`failedLogins` does not go up.** Then 401 "The
       passkey check failed. Try again or sign in with your password."
  6. On success: store `newCounter` and `lastUsedAt`, then `startSession(req, reply, user, ' (passkey)')`.
- **Rename and remove:** your own passkeys only, otherwise 404. Removing audits `Removed the passkey "<name>"`.

**Interfaces:**
- Consumes: Task 1's `relyingParty`, `issueChallenge`, `takeChallenge`, `deviceName`, `SoftAuthenticator`.
- Produces, for Task 3: the routes and response shapes in the table above. `GET /auth/two-step` gains `passkeys: number`.
